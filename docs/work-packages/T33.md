## 2. 为什么需要重做中间层

当前链路已经能运行，但属于“阈值分类 + 目录先验排序”，不是严格 Roofline：

1. 指标按 launch 取最大值；一个耗时很小的 launch 可能决定整个算子的标签。
2. CSV 保存了 unit，但分类器没有验证和换算单位。
3. `ncu_full` 只表示某指标在至少一个 launch 出现，不代表重要 launch 均完整。
4. 固定阈值 `20 us / 40% / 60% / 70%` 未按 GPU、NCU 版本、dtype、shape 校准。
5. 单标签采用 `numerical → launch → parallel → memory → compute → latency` 短路，
   无法表达“既欠并行又受内存限制”。
6. 当前分数主要来自目录字符串 `low/medium/high`；NCU 只控制方法是否匹配，信号强度、
   证据覆盖和实际成本几乎不进入排序。
7. 主循环固定使用 `HardwareFacts.sm89_reference()`，没有从当前 GPU evidence 注入 SM 数量、
   峰值、带宽和真实 compute capability。

因此当前输出只能称为“可解释假设”。T33 的目标不是把它包装成更精确的伪分数，而是建立
从原始证据到实验决策的完整数据契约。

## 3. 不变信任边界

以下规则优先于任何分类或排序算法：

- profiling 只产生诊断假设；正确性、正式性能和晋升仍由可信 evaluator/父服务决定。
- baseline profiling 与 candidate timing 分开；NCU duration 永不进入 speedup 计算。
- 缺失、不可用、单位未知、范围非法均为 MISSING/INVALID，不得填零。
- 每条机制结论必须指向具体 launch、metric、单位、报告 hash 和 profile identity。
- 多 workload 不得只聚合获益 shape；权重和必测集合在看结果前冻结。
- 若仍沿用 ADR-0003 特权租约，不可信候选不得进入；候选 profiling 需要新的信任域设计和 ADR。
- 硬件/驱动/NCU/capture/problem 任一身份变化，旧派生特征和方法历史默认不可直接复用。
- 阈值、评分权重和聚合规则均版本化；不能为了让某次实验“看起来正确”临时修改。

## 4. 目标流水线

```text
Pinned workload + hardware identity + capture protocol
    ↓
NCU raw report（逐 launch，原始值/单位/可用性）
    ↓
Schema/单位/范围校验与 metric alias 解析
    ↓
逐 launch 派生量（时间占比、吞吐、occupancy、bytes、FLOPs、AI）
    ↓
逐 kernel 聚合 + 算子级时间加权聚合 + 覆盖/稳定性评估
    ↓
多轴瓶颈特征（severity 与 confidence 分离）
    ↓
方法硬守卫 → 必需证据 → 正/反信号 → 方法偏序或可选效用分
    ↓
多样化 MethodPlan（假设、目标改动、预测观察、证伪条件、预计成本）
    ↓
单因素候选 → 正确性 → 正式 timing → 独立确认
    ↓
AttemptOutcome 回写方法历史；必要时追加诊断，不把失败删掉
```

每次 launch 至少保留：

```json

  "invalid": []

```

禁止只保留最大值后丢掉 launch 级来源。相同 kernel 名的多次 launch 可以另建 kernel-group，
但不能用名称前缀误合并两个不同模板/shape 的 kernel。

### 5.3 缺失与无效值

每个需要但不可用的字段记录结构化原因：

```json
{

  "state": "missing",

  "affected_launches": ["2", "3"]
}
```

`0` 仅代表 NCU 明确测得零。`None`/缺键代表没有数值。字符串 `n/a` 不进入数学运算。

## 6. 指标规范化

### 6.1 Metric schema 与 alias

新增版本化 `MetricDefinition`：

- canonical name；
- 支持的 NCU metric aliases/版本范围；
- quantity（time、percent、bytes、count、rate、instructions）；
- 允许单位与到 canonical unit 的转换；
- 合法范围；
- 可聚合方式；
- 适用 GPU/compute capability；
- 指标语义链接或冻结说明。

不能仅因名字相似就自动 alias。未知 metric 可以原样保留，但不能进入规则。

### 6.2 单位

canonical units：时间统一 `us`，字节统一 `byte`，速率统一 `byte/s`，比例统一 `[0, 1]`，
计数保持整数。示例：

```text
ns → us: value / 1_000
ms → us: value × 1_000
%  → ratio: value / 100
KiB → byte: value × 1024
GB/s 与 GiB/s 不得混用
```

单位缺失或不在 allowlist 时，该派生量为 MISSING。不得用 MetricCatalog 中的期望单位覆盖报告
实际单位。对 `launch__occupancy_limit_registers` 等语义可能随版本变化的指标，先用真实报告和
官方定义冻结其 quantity，再设阈值。

### 6.3 范围与一致性

- 比例必须在 `[0, 1]`（允许小量浮点误差后 clamp，并记录修正）。
- duration、bytes、FLOPs、grid、block、registers 不得为负。
- block threads 不得超过设备能力；grid 与 NCU 文本列交叉检查。
- report 中 GPU/CC 必须与 manifest/probe 相符。
- 同一 capture 中 unit 漂移、metric 重名不同义、launch ID 重复均使 quality 降级或拒绝派生。

## 7. Launch 选择和关联

### 7.1 目标范围

profile driver 应明确标记一次目标 operator 的范围，优先使用父端生成的 NVTX range、进程/stream
身份和调用序号；kernel name 只作为辅助证据。需要排除：

- 初始化、JIT、随机输入生成；
- warmup；
- 与目标无关的 allocator/runtime kernel；
- NCU replay 自身重复产生但不代表额外 operator 工作的记录。

排除规则必须写入 capture protocol，原始 launch 仍保留，不能静默删除。

### 7.2 时间贡献

对目标范围内 launch 计算：

```text
T_gpu = Σ duration_i
time_share_i = duration_i / T_gpu
```

定义 dominant set 为按 `time_share` 降序累计达到预先冻结比例（建议初值 90%）的 launches。
单个 `<1%` 时间占比的 launch 不得仅凭极值决定算子级瓶颈，但其异常仍保留在 per-launch 诊断。

注意：`Σ kernel duration` 不等于 operator wall time；并发 stream 会重叠，launch/host gap 也未包含。
需要 launch-overhead 结论时，组合正式 operator 时间、CUDA API/NSYS 或已校准 launch latency；
只有 NCU kernel duration 时将该结论标为 hypothesis，而不是 confirmed。

## 8. 聚合逻辑

聚合分三层，禁止一个 `max()` 同时服务所有语义。

### 8.1 同一 kernel-group

对重复 launch 保存：count、sum、median、p10/p90、MAD/CV、min/max。重复不足时 stability=MISSING。
极值用于发现异常，不直接代表常态瓶颈。

### 8.2 算子级

推荐规则：

| 指标 | 主聚合 | 辅助聚合 | 说明 |
|---|---|---|---|
| duration | sum/critical-path estimate | median、p90 | 不能只取 max |
| DRAM/SM throughput ratio | duration-weighted mean over dominant set | p90/max + launch 引用 | 小 kernel 极值不主导 |
| active warps/occupancy | duration-weighted harmonic/mean | p10 | 低值风险比高值更重要 |
| registers/thread | dominant launch 的 weighted p90 | max | 与 block size、spill 一起解释 |
| grid blocks | 每 launch 保留；按 time share 报告 | min | 不应把不同 kernel grid 相加 |
| bytes/FLOPs | sum（无重叠重复计数时） | per-launch | 用于 Roofline |
| stalls | weighted vector | dominant reason per launch | 不压成单一 max |

若某指标仅覆盖部分 dominant launches，同时返回 `coverage_time_share`。例如 DRAM metric 覆盖了
80% 的 GPU 时间，就记录 0.8；不得因为它在一个 launch 出现就称为 full。

### 8.3 多 workload

每个 workload 独立生成特征和计划。跨 workload 只按预先冻结的权重形成：

- worst-case guard；
- weighted expected gain；
- regression count；
- coverage。

不得先看哪个 shape 获益再改变权重。方法可以只适用于一个 shape，但最终 dispatch 和晋升必须
满足 T21 的完整 workload 契约。

## 9. Roofline 派生（可选但推荐）

### 9.1 必需量

```text
F = executed FLOPs（按 dtype/标量或 Tensor Core 类型分开）
B = DRAM bytes read + write
T = kernel duration seconds
AI = F / B                         [FLOP/byte]
P_achieved = F / T                 [FLOP/s]
BW_achieved = B / T                [byte/s]
P_roof = min(P_compute_peak, AI × BW_peak)
roof_efficiency = P_achieved / P_roof
ridge_point = P_compute_peak / BW_peak
```

峰值优先用同机、同 dtype、同 clock policy 的校准微基准；datasheet 只能标为低一级来源。Tensor Core
FLOPs、稀疏/低精度、FMA×2、重放次数必须按冻结定义计数。无法可靠得到 F 或 B 时，不计算 AI，
退回吞吐/静态规则并将 roofline coverage 标为 missing。

### 9.2 输出

Roofline 不直接输出“采用某方法”，而输出：

```json
{
  "arithmetic_intensity": 3.8,
  "ridge_point": 27.1,
  "achieved_flops_per_s": 1.2e12,
  "achieved_bytes_per_s": 3.1e11,
  "roof_flops_per_s": 3.4e12,
  "roof_efficiency": 0.35,
  "limiting_roof": "memory",
  "confidence": 0.78,
  "evidence_launches": ["0", "2"]
}
```

`limiting_roof=memory` 只说明当前算术强度下 Roofline 的上界，不自动证明 coalescing/fusion 一定有效；
还需交易效率、缓存、访问模式和算法结构证据。

## 10. 多轴瓶颈特征

不要先短路成唯一标签。每个轴保存 severity、confidence、evidence 和 counter-evidence：

```json
{
  "axis": "memory_pressure",
  "severity": 0.82,
  "confidence": 0.71,
  "evidence": ["dram weighted=0.79 coverage=0.93", "roof limiting=memory"],
  "counter_evidence": ["L2 hit rate high"],
  "missing": ["global load efficiency"],
  "scope": "operator|kernel:<id>"
}
```

建议轴：

- correctness/numerical（来自 evaluator/history，不来自 NCU）；
- launch overhead；
- parallel deficit；
- memory bandwidth/traffic；
- cache/locality/coalescing；
- compute throughput/instruction mix；
- occupancy/resource pressure；
- dependency/stall latency；
- synchronization/serialization；
- algorithmic excess work。

### 10.1 初始 severity 函数

允许使用版本化 piecewise 规则，而不是假装为概率：

```text
sat(x; low, high) = clip((x - low) / (high - low), 0, 1)

memory_pressure = sat(weighted_dram_ratio; 0.50, 0.85)
compute_pressure = sat(weighted_sm_ratio; 0.50, 0.85)
low_warps = 1 - sat(weighted_active_warps_ratio; 0.25, 0.60)
grid_deficit_i = clip(1 - grid_blocks_i / (waves_target × sm_count), 0, 1)
```

这些只是初始 severity，不是成功概率。阈值必须写入 `feature_protocol_version`，按 GPU 家族校准并做
敏感性分析。若有 Roofline，memory/compute severity 应结合 roof gap；不能仅按 throughput 二选一。

### 10.2 Confidence 单独计算

confidence 反映证据质量，不等于瓶颈强度。建议组成：

- identity 完整；
- unit/schema 已验证；
- dominant time coverage；
- 重复稳定性；
- 指标是否直接测得而非静态先验；
- 硬件峰值来源；
- 多个独立信号是否一致。

任何关键项 MISSING 时保留 severity hypothesis，但降低 confidence 并列出原因。不要把缺失输入当成
`severity=0`。

## 11. Profiling 特征到优化方法的匹配

### 11.1 每个方法的机器可读契约

把 methods catalog 扩展为：

```json
{
  "method_id": "memory.coalesce_contiguous_access",
  "hard_guards": ["backend=triton", "dtype supported"],
  "required_evidence": ["access_pattern OR dram_transactions"],
  "positive_signals": ["memory_pressure", "poor_transaction_efficiency"],
  "counter_signals": ["traffic already minimal", "compute roof limiting"],
  "compatible_axes": ["memory_pressure", "cache_locality"],
  "conflicts": ["method ids that cannot be isolated together"],
  "expected_observations": ["DRAM bytes decrease", "formal latency decreases"],
  "falsification": ["bytes unchanged and latency CI shows no gain"],
  "cost_model": {"compile": "low", "gpu": "low", "token": "medium"}
}
```

自然语言描述可继续用于 prompt，但是否匹配必须来自版本化规则，不能让 LLM 自己决定“我适用”。

### 11.2 匹配顺序

1. **正确性优先**：编译/数值/越界失败先进入修复方法，不参与性能方法竞争。
2. **硬守卫**：backend、CC、dtype、shape、依赖、共享内存、确定性契约不满足则拒绝。
3. **必需证据**：必要字段缺失时结果为 `insufficient_evidence`，不是“不适用”。
4. **正信号**：至少一个直接或明确静态信号命中。
5. **反信号**：记录反例；强反信号可拒绝，弱反信号降低优先级。
6. **冲突/单因素**：本轮只授权一个主要机制；安全 mask/累加精度作为 guard 随行。
7. **历史**：相同问题身份上的失败降低优先级；infra failure 不惩罚方法。
8. **多样性**：预算允许时保留不同机制族的 Pareto 候选，而不是 Top-K 全是同族变体。

### 11.3 初始映射表

| 特征/证据 | 优先方法族 | 必查反证 |
|---|---|---|
| launch overhead 高、多短 kernel | fusion、multi-kernel merge、host cleanup | 是否已有融合；正式 operator 时间中 launch 占比是否可见 |
| grid deficit 高 | grid expansion、split-K、split reduction | 额外归约/原子成本、K/axis 是否足够大 |
| occupancy/resource pressure | block/warp tuning、register reduction、staging 调整 | occupancy 是否真是限制；spill/shared memory 情况 |
| memory roof + 多余流量 | fusion、online streaming、intermediate elimination | 必需输出流量下限、cache 命中、算法正确性 |
| memory pressure + 访问低效 | coalescing、vectorization、layout/swizzle | 对齐、连续维、transaction efficiency |
| compute roof + 标量 FMA | tensor core/tl.dot、精度内变换 | dtype/shape/容差/CC 支持 |
| compute 中 transcendental 占比高 | algebraic strength reduction | 误差上界和特殊值 |
| stall/dependency 高 | software pipeline、num_stages、warp specialization | occupancy/shared memory 退化、硬件能力 |
| reduction/同步占主导 | warp/block staged、two-pass、persistent | 确定性、数值累计、axis/shape |
| mask 导致无效工作 | block early-exit、稀疏/结构化路径 | mask 真正稀疏度、分支发散 |
| NaN/Inf/大误差 | stable reduction、FP32 accumulator、完整 mask | 先恢复正确性，不声称性能收益 |

## 12. 是否需要总分

### 12.1 推荐默认：无总分的分层偏序

数据尚未校准时，默认用确定性字典序：

```text
correctness repair
→ hard direct NCU match with high confidence
→ direct NCU match with partial confidence
→ task/static prior
→ fallback baseline method
```

同层内按：强反证数量、历史失败次数、预计成本档、机制族多样性、catalog 稳定顺序选择。
优点是不会把不可比较的 0.73 和 0.68 伪装成精确概率。

### 12.2 可选：显式效用分

如果需要预算优化，可计算但必须展示分量：

```text
utility =
    applicability
    × evidence_confidence
    × expected_log_speedup
    × empirical_success
    / expected_total_cost
    + exploration_bonus
```

- `applicability`：规则匹配强度，不是模型自评。
- `expected_log_speedup`：来自相同 GPU/算子族/shape bucket 的历史；没有数据时用宽先验。
- `empirical_success`：Beta-Bernoulli 或分层贝叶斯后验；失败和无收益都进入分母。
- `expected_total_cost`：编译墙钟、GPU lease 秒、autotune 次数、token/费用；不得只按类别写 1/1.5。
- `exploration_bonus`：只控制探索，不伪装成收益。

所有分量、版本、输入 evidence ref 和最终 utility 写入 journal。分差小于预设不确定区间时视为并列，
按多样性或较低成本选，不宣称排名显著。

### 12.3 后续机器学习

只有积累足够、身份一致的历史后再比较 contextual bandit/learning-to-rank：

- context：GPU、driver、backend、算子族、dtype、shape、基线代码特征、瓶颈轴；
- action：method id + 参数空间版本；
- outcome：编译、正确、正式 speedup CI、GPU 秒、token、终态；
- censoring：预算中断、infra failure、未执行必须单列；
- 训练/评估按 problem/GPU 时间切分，避免同题泄漏；
- 与无 profile、固定规则、随机/轮转、当前启发式做等预算对照。

在此之前不引入黑箱模型；规则 + 可更新先验更容易审计。

## 13. MethodPlan 与模型提示

每个计划项必须包含：

- `method_id`、catalog/protocol 版本；
- 引用的 profile evidence 和 launch IDs；
- severity/confidence/coverage，不只给一个标签；
- 假设与目标改动；
- 只允许的一个主要因素；
- 参数空间与硬守卫；
- 预测观察（例如 bytes、occupancy、正式 latency 应怎样变化）；
- 证伪条件；
- 预计成本及来源；
- 反证与缺失字段；
- 排序方式（lexicographic/utility）及全部分量。

模型只看到有界摘要和必要代码上下文；原始 NCU 报告通过 evidence ref 留存，不整份塞入 prompt。
提示必须说明 profiling 是 baseline evidence 和 untrusted diagnostic data，候选不能修改 evaluator、容差、
计时范围或自报结果。

## 14. 执行结果回写

每个 attempt 写入：

```json
{
  "method_id": "...",
  "method_plan_sha256": "...",
  "candidate_sha256": "...",
  "stage": "generation|policy|evaluate|correctness_pro|timing|confirm",
  "outcome": "compile_failed|incorrect|valid_no_gain|promoted|infra_error",
  "formal_speedup_ci": null,
  "gpu_seconds": 0,
  "tokens": 0,
  "failure_diagnostics": {},
  "hypothesis_status": "not_tested|falsified|supported_not_causal|confirmed_by_ablation"
}
```

- 编译失败：反馈结构化编译错误，方法成功先验下降；不进入 timing。
- 正确性失败：保存误差/失败类型，优先数值修复；不计为性能反例。
- 正确但无收益：是方法在该 context 的负结果，必须进入历史。
- 晋升：仅表示正式性能确认；机制最多为 `supported_not_causal`。
- profiling/计时 infra failure：不惩罚方法，成本仍结算。
- 因果确认：需要单因素消融或等价证据，属于 T17/T25。

resume 必须从持久化 plan 和 attempt 重建完全相同的下一决策；不能依赖进程内随机顺序。若使用随机
探索，保存 RNG seed/state 和抽样概率。

## 15. 代码职责建议

| 层 | 建议对象/模块 | 职责 |
|---|---|---|
| Domain | `ProfileEvidenceV2`、`BottleneckFeature`、`MethodMatch`、`RankingDecision` | plain data、校验、序列化；不导入 adapter |
| Profiling adapter | metric definitions、unit normalizer、NCU alias resolver | NCU 特有解析和规范化 |
| Analysis service | launch association、aggregation、roofline、quality | 纯函数，可用 fixture CPU 测试 |
| Generator | method matcher、lexicographic/utility policy | evidence → MethodPlan，不决定结果 |
| Optimization loop | 调用、预算、持久化、resume | 不嵌入 NCU metric 名和方法阈值 |
| Evaluator | correctness/timing/promotion | 独立可信裁决 |

当前 `generators.classify` 中镜像一份 metric 名称只能作为临时边界。目标应由版本化、adapter-neutral
feature schema 隔离：generator 消费 `memory_pressure` 等领域特征，不直接依赖 NCU 字段。

## 16. 拆包顺序

### T33a：Metric schema、单位和证据质量

- 实现 alias、unit conversion、范围验证、per-launch missing/invalid。
- 修复 duration 单位假设和 occupancy-limit 指标语义。
- 不改变现有 planner 选择，先双写 V1/V2 evidence 做兼容对照。

### T33b：硬件身份、launch 关联和聚合

- GPU probe/NCU 注入真实 CC、SM 数量、峰值来源。
- 目标范围标记、dominant launches、time-share coverage、重复稳定性。
- 新旧 max 聚合并行输出，报告差异，不静默切换实验协议。

### T33c：多轴特征与可选 Roofline

- 先实现 severity/confidence/反证/MISSING；保留旧单标签为兼容展示字段。
- 在 FLOPs/bytes/峰值齐全的路径计算 Roofline；不齐全时明确降级。
- 阈值协议版本化并在至少两类算子上做敏感性测试。

### T33d：方法契约和无总分匹配

- catalog 增加 guards/required/positive/counter/falsification/cost schema。
- 实现分层偏序和机制族多样性；完整记录 refusal/insufficient evidence。
- prompt 引用具体 evidence，不把单标签当结论。

### T33e：可选成本/历史排序

- 从真实 journal 估计 GPU/token/编译成本。
- 引入可重算 utility components；没有校准数据时保持 lexicographic 默认。
- 若试验 Bayesian/bandit，单独版本和离线回放，不替换可信 evaluator。

### T33f：GPU 验收与研究消融

- Ubuntu + 至少一张声明 GPU 上跑真实 NCU。
- 覆盖短 elementwise、多 kernel 链、memory-heavy reduction、compute-heavy matmul、small-grid。
- 做 current heuristic vs T33 no-score vs optional utility 的等预算比较。
- 完成去 profile、去历史、去结构化假设消融；负结果完整保留。

## 17. 验收规格

以下命令是目标接口；子包实现前可调整文件名，但不得削弱观察条件。

| 检查 ID | 层级 | 目标命令/入口 | 必须观察到 | 当前状态 |
|---|---|---|---|---|
| A1 单位规范化 | CPU | `pytest tests/test_profile_normalization.py` | ns/us 等价；未知单位 MISSING；非法范围拒绝 | NOT_RUN |
| A2 launch 聚合 | CPU | `pytest tests/test_profile_aggregation.py` | 小时间占比极值不主导；dominant coverage 正确；并发语义不伪造 | NOT_RUN |
| A3 Roofline | CPU | `pytest tests/test_roofline.py` | 合成 FLOPs/bytes/peak 可重算；缺任一必需量不输出伪 AI | NOT_RUN |
| A4 多轴分类 | CPU | `pytest tests/test_bottleneck_features.py` | memory+parallel 可同时存在；severity/confidence 分离 | NOT_RUN |
| A5 方法匹配 | CPU | `pytest tests/test_method_matching_v2.py` | guard、必需证据、正反信号、MISSING、偏序、多样性 | NOT_RUN |
| A6 排序重算 | CPU | `pytest tests/test_method_ranking_v2.py` | 无分模式稳定；有分模式分量完整且可重算 | NOT_RUN |
| A7 resume | CPU | `pytest tests/test_resume_request_parity.py` | 连续/恢复的 plan 和下一请求一致；不重复计费 | NOT_RUN |
| A8 真实 NCU | GPU | `kernelagent profile ...` + 固定 smoke | 单位/身份/launch/coverage 来自真实报告，不用 fixture 冒充 | NOT_RUN |
| A9 闭环 | GPU/LIVE_MODEL | 固定候选后真实模型有界跑 | profile→plan→正确性→timing→反馈；失败也是合法终态 | NOT_RUN |
| A10 消融 | GPU/REVIEW | T25 experiment bundle | 与当前规则/无 profile 等预算比较，结论可追溯 | NOT_RUN |

必要反例：

- NCU 用 ns 输出 duration；
- 某 metric 仅存在于耗时 0.5% 的 launch；
- 一个 launch DRAM 高、另一个 SM 高；
- metric 在部分 dominant launch 缺失；
- report GPU UUID/CC 与 manifest 不同；
- occupancy metric 单位错误；
- FLOPs/bytes/peak 任一缺失；
- 方法硬件能力不满足；
- 高 expected gain 但有强 counter-evidence；
- infra failure 与真实 no-gain；
- resume 前 evidence 被篡改。

## 18. 迁移策略

1. V1 evidence 保持只读兼容，新增 V2 双写；report 显示 analyzer/protocol version。
2. 先 shadow 运行新分析器，不改变方法选择；比较分类和计划差异。
3. GPU 固定 fixture/真实报告通过后，配置开关启用 V2 lexicographic planner。
4. 正式实验不得混合 planner/threshold 版本；resume 发现版本漂移应拒绝或继续旧版本。
5. 旧 `score` 字段若保留，重命名/标注为 `heuristic_rank_score_uncalibrated`，避免被解释成概率。
6. 关键 schema、候选 profiling 信任域或晋升证据变化需写 ADR。

## 19. 开放决策

- 首个真实目标 GPU 是否只冻结 RTX 4060 SM89，还是同时支持数据中心 GPU。
- NCU 版本范围和不同架构 metric alias 表由哪些真实报告覆盖。
- 峰值采用微基准还是 datasheet；时钟无法锁定时如何降级 confidence。
- baseline 为 eager/compile 哪一轨，是否两者都 profile；必须与报告标签一致。
- 是否需要 NSYS/CUPTI 提供 host launch gap；NCU 单独不能确认完整 launch overhead。
- 候选 profiling 是否值得新增非特权隔离路径；在 ADR 前保持 NOT_RUN。
- 多 workload 权重、dominant launch 90%、tiny launch 1% 等初值需在正式实验前冻结。
- 数据规模达到什么门槛后才允许启用经验分或 bandit；门槛应预注册。

## 20. 完成定义

T33 只有在 T33a–T33f 的必需检查完成后才能 ACCEPTED。文档、schema 骨架、fixture 单测或一次
成功 profile 均不等于完成。GPU/LIVE_MODEL 未执行保持 NOT_RUN；机器学习排序没有足够数据时可以
不实现，默认的无总分偏序仍须完成真实闭环与等预算验收。
