# 开发任务与验收计划

日期：2026-09-12
设计基线：[NVIDIA 算子优化 Agent 设计文档](NVIDIA算子优化Agent设计文档.md)，v0.1。
本文件将设计落实为开发工作包；不是已完成实现或实验结果。

## 1. 在有限额度下开发的基本方式

**以一个可验收工作包为会话单位，以仓库文件保存状态，以实际检查决定完成。** 不向一个会话下达“实现整套系统直到结束”，也不把编写所有类骨架当作一个阶段完成。

Codex 官方说明中的五小时是使用量窗口，不是保证可连续工作的五小时；复杂度、上下文和模型影响消耗，且可能还有周限额。新建任务用于减少无关上下文，不能重置账户额度。具体剩余额度以账户用量界面为准。本计划不承诺一个额度窗口能完成多少工作包。[官方说明](https://developers.openai.com/codex/pricing/)

需要分清三种预算：

| 预算 | 用途 | 本项目如何控制 |
|---|---|---|
| 开发助手额度 | 让 Codex 编写、审查和修复项目 | 一次一个小包；局部阅读；检查点；避免反复全仓调研 |
| agent 运行时模型预算 | 将来优化算子时生成假设/代码 | `ModelClient` 可替换；token/请求成本入账；API 或自托管模型由部署配置提供 |
| GPU 实验预算 | 编译、正确性、计时、profiling | 独立 worker；作业 ID；超时；持久化结果；每次试验真实计费 |

不能假设 ChatGPT 会员自动给开发出的 Python 程序提供无限或包含在会员内的 API 调用。离线开发可使用录制响应/假客户端验证控制流程，但最终验收必须包含真实模型调用和真实 GPU 执行；提供方与凭据稍后配置，不把录制响应当成生成能力。

开发侧建议：接口设计、测量协议、晋升与安全边界使用更强推理；明确的 adapter/序列化/CLI 等局部实现可用账户中可用且较省额度的模型。模型选择不改变验收标准，不假设所有账户有相同模型列表。默认不启用多个开发子 agent，以免并发快速消耗额度。

## 2. 一个工作包应该多大

一个包最好只改变一个主要行为或一条薄的纵向流程，例如“从固定 KernelBench 快照读取并导出任务清单”，而不是“完成全部 benchmark 和 agent”。以一次约 30–90 分钟的专注实现与验证为切分参考，时间仅为工作组织目标，不能视为模型耗额预测或交付保证。

遇到接口未知、依赖安装冲突、跨多个后端时，先拆成探测包和实现包。连续两次修复仍不能缩小失败原因时，写出最小复现并拆包；不要在同一上下文里无限扩大修改范围。

每个包必须同时定义：

1. 对应设计章节和要实现的用户可观察行为。
2. 前置依赖、已有接口、固定输入或 fixture。
3. 允许修改的区域，以及本包不实现的能力。
4. 可以运行的检查及预期结果，至少一个成功例和一个有意义的失败例。
5. 原始证据的输出位置、完成状态、下一步命令。

允许的代码区域是防止范围膨胀的提示，不是僵硬禁止修复必要相邻接口。若确需扩大范围，先记录原因、受影响契约与验证，再决定在本包处理还是拆出新包；只有改变用户目标或关键运行规则时才需要用户决策。

## 3. 统一状态与完成定义

使用 `TODO → IN_PROGRESS → READY_FOR_ACCEPTANCE → ACCEPTED`，另有 `BLOCKED`。`ACCEPTED` 必须有机器检查结果和证据路径；“代码已写”“agent 自述正常”“测试全跳过”都不能验收。

每个包记录 `CPU / GPU / LIVE_MODEL / REVIEW` 四种检查状态：`PASS / FAIL / NOT_RUN / N/A`。硬件包允许代码已准备好而 GPU 为 `NOT_RUN`，此时最多 `READY_FOR_ACCEPTANCE`。离线包本来就不要求 GPU，可将其设为 N/A 后验收，但不能借此宣布整个系统可运行。

完成的统一条件：

- 指定行为可重现，必要正反例通过，相关原有回归通过。
- 没有用 mock、硬编码 PASS、TODO/no-op 替代本包承诺的生产功能。
- 错误返回符合 domain schema；不把错误变成正常分数。
- 数据契约与依赖方向符合设计；新增第三方优先通过 adapter 接入。
- 结果绑定代码版本/内容 hash、输入、协议和环境；日志与命令可查。
- task board、交接记录和证据索引已更新；存在未知项就明确保留。

审查和测试是两种证据：审查检查设计边界，测试检查已覆盖行为。新会话进行一次聚焦审查可减少作者盲点，但不是完全独立验证；不能用“另一个模型说没问题”替代运行结果。

| **T22 长实验与结果导出** | T08、T10、T16 | CLI 配置、远程 transport/作业 ID、报告、完整复现导出 | 控制会话退出后独立作业状态可查；重连能读到结果；导出包可重新验证 candidate；失败/无改进都生成报告 | §11–12 |
| **T23 整体验收与对抗回归** | T06–T22 | clean worker 复现、端到端、故障注入、规则检查 | 第 7 节发布门槛全通过；不能只有单元测试/假模型；已知攻击反例回归；主循环不依赖具体 backend | §13–15 |
| **T24 正式实验冻结与运行** | T23 | 预先固定清单、模型/资源配置、A/B/C/D 对照、消融 | 先冻结再跑；至少 3 次独立搜索种子作为初始协议；统一预算和起点；失败全记录；最终独立确认 | §9.5、13–14 |
| **T25 研究分析与实验包** | T24 | fast_p/覆盖率/成本曲线、方法消融、逐任务表、复现说明 | 每条图表记录可追溯原始实验；不删除负结果；结论区分实现能力与优于基线的实测证据 | §13–15 |

真实模型不保证每个任务一次生成就正确。T12 的真实闭环可使用预先冻结、足够简单的 smoke 问题和有限修复预算；若仍失败，真实验收就是失败，不能换成回放输出过关。T11 同理。

T06/T07 的对抗用例验证已知风险，不表示防御任意恶意 GPU 程序。限额小也不能因此省掉对计时和 evaluator 的核验，否则会把后续大量 GPU 时间花在虚假收益上。

## 5. 先后顺序与阶段门

推荐先做可运行的薄闭环，再扩展，不先耗尽额度搭建几十个空接口。

| 阶段门 | 工作包 | 阶段验收 |
|---|---|---|
| **G0 地基与输入** | T00–T03 | domain + 原版任务清单 + 实际 GPU 环境报告；GPU 未就绪时明确保留 T03 |
| **G1 可信实验机** | T04–T10 | 给已知候选就能自动验证、计时、记录、拒绝错误、恢复任务；此时还不是完整生成 agent |
| **G2 自动优化闭环** | T11–T16 | 上游策略和自有生成/调参共享 evaluator；实际 NCU→方法提案→候选→确认闭环可运行 |
| **G3 扩展与完整系统** | T17–T23 | 机制证据、两个额外 benchmark、CUDA/CUTLASS、多 workload、远程实验与复现通过 |
| **G4 实验结论** | T24–T25 | 固定协议的对照/消融全部有结果；结果好坏都可发表为诚实实验记录 |

这不是“26 个会话一定完成”：复杂的 worker、计时、后端包很可能各需要多个子包和修复会话。应按验收收敛，而不是按会话数量宣布完成。

完整 v1 覆盖原设计的主干与明确第二阶段扩展。TileLang/CuTe DSL 的额外独立 backend、清华 TritonBench 全量适配、RL 训练、Kubernetes/多机复杂调度在原设计中为后续方向，单独列入 vNext，不用其无限扩大 v1。若用户希望这些也纳入当前 release，应新增独立任务与验收，不藏在“支持多后端”的描述里。

## 6. 每个额度窗口的工作节奏

一个窗口只装入当前实际能完成的工作包，不提前填满五小时：

1. 开始读取 AGENTS、task board、最近交接和对应设计章节；检查代码实际状态，避免相信陈旧摘要。
2. 确认一个 ready 工作包，补全卡片中的精确检查命令与预期结果。
3. 局部实现 → 相关检查 → 修复。保持可运行检查点，不把下一包塞进来。
4. 在达到验收门或额度不足以完成下一轮时，立即保存交接；不等待系统强制中断。
5. 下一窗口继续同一未完成包，或给已完成包做聚焦审查，再进入下一包。

可以把“约 15%–20% 的剩余额度用于收尾”作为个人习惯，但使用量消耗不可精确预测，也不保证工具随时能读到配额。更可靠的做法是每次 meaningful check 后更新状态，随时可中断。

适合普通脚本独立完成的安装、编译、长 benchmark 不需要助手不断轮询。T22 建好后，worker 作业由服务/作业系统持有，结果落盘，额度恢复后再分析。**会话中的临时工具进程不等于已具备可靠后台执行能力**，在 T22 验收前不要假设关闭会话仍一定继续。

不要为节省上下文每轮重读 3 万字设计或所有 research 快照。保留一页固定约束 + 当前卡片 + 相关源码。每阶段门再做跨模块设计核查，发现偏离时用小补丁修正，避免最后大返工。

## 7. “开发完整”和“实验成功”的不同验收

### 7.1 v1 系统完成门槛

以下全部满足，才可声明“v1 已完整开发并通过声明环境验收”：

- T00–T23 的所有必需检查通过，GPU/LIVE_MODEL 没有被 mock/skip 替代。
- 在一个声明的 NVIDIA GPU 环境中，以真实模型与 worker 跑通至少一个有界自动搜索；会产生正确候选并执行确认/晋升或无改进决策。
- KernelBench 冻结的 L1 开发子集，以及事先选定的 L2 融合任务可全部终止并记账。自动生成失败允许作为任务结果，但 evaluator 基础能力与已知正确候选回归不能失败。
- Meta tritonbench、FlashInfer-Bench、Triton、CUDA/CUTLASS 的指定 smoke 路径真实运行；仅承诺清单内验证范围，不说“所有算子/所有 NVIDIA GPU 都支持”。
- 所有晋升包含 E0/E1/E2；解释要求的任务具备 E3；因果主张满足 E4 或明确标为待验证。
- 在编译、评测和结果写入等故障点中断后能恢复，预算不会丢失或重复结算。
- 另一干净 worker 环境能按说明复验导出的最终候选和报告来源。

至少一个真实有收益的候选可以作为演示目标，但不设为整个软件正确性的唯一标准。系统能诚实判定无收益，本身是正确行为。

### 7.2 研究实验完成门槛

T24–T25 全部完成才叫“实验完成”。要求协议冻结、对照/消融、成本与负结果完整，不预设一定打败 Meta KernelAgent。若论文假设是“证据降低无效搜索成本”，必须用等预算实验支持；类图漂亮、流程完整不能证明研究假设。

三次独立搜索种子是本计划建议的初始下限，不保证统计功效；正式任务数/重复数根据预实验噪声与可用资源预先调整。搜索种子、正确性输入种子和确认计时批次分别记录，不能当成同一种重复。

## 8. 防止偏离设计的低成本机制

| 设计约束 | 可执行防线 | 首次引入 |
|---|---|---|
| Domain 不依赖具体工具 | import/依赖边界检查 | T01 |
| evaluator 独立掌握成功与晋升 | 篡改结果文件/PASS stdout 反例 | T04–T06 |
| 时间与 profile 不混用 | result schema 区分来源，promotion 拒绝 profile duration | T07/T09 |
| 没有证据不晋升 | 缺 hash/缺验证/协议不一致反例 | T08/T09 |
| 任务与评分不因结果变化 | 冻结 manifest，expected task 集合校验 | T02/T09 |
| 复用已有工具 | adapter 的上游调用对照 + 依赖来源审查 | T05/T14/T18–T20 |
| 方法与实现分离 | 同一 Method 多参数实例、同一循环多 Generator 合同测试 | T13/T16 |
| 可取消、可恢复、有预算 | 故障注入和预算守恒检查 | T10/T22 |
| 硬件/形状是能力而非深继承 | guard 合同测试；主循环不分支 benchmark/backend 名称 | T18–T21 |

关键接口或实验协议变更记录为 ADR：原决定、变更原因、受影响任务/测试、迁移策略。普通实现细节由开发者自行处理；不能通过把验收阈值放松、删除失败用例或缩小清单来“修好”失败。

## 9. 可直接使用的会话指令

### 开发一个包

> 请按 AGENTS.md、docs/开发任务与验收计划.md 和 docs/task-board.json，只推进工作包 Txx。先检查依赖是否实际验收，再阅读对应设计章节，建立本包具体检查命令与正反例。完成实现和必要验证，记录证据与交接；不要自动扩展到下一包。没有 GPU/真实模型时如实标记待验收，不使用 mock 声称真实能力完成。优先复用上游工具，接口变更记录原因。

### 聚焦验收

> 请验收 Txx，对照工作包卡片和原设计检查代码与结果，不只复述作者总结。运行该包指定检查，审查关键边界和失败分支。给出 PASS/FAIL/NOT_RUN、证据路径及阻塞项；不要通过修改验收规则使其通过。若发现问题，列出最小修复范围，必要时在本包内修复并重新验证。

### 额度不足时交接

> 请在最近的安全检查点收尾：保存文件、更新 task board 和 docs/handoffs/current.md，列出已完成行为、尚未通过检查、实际运行命令/结果、活动作业 ID、代码状态、下一条命令。不要启动新的大步骤，也不要把待验证状态标成完成。

### 恢复开发

> 请先读取 AGENTS.md、task board 和 current handoff，核实实际代码/作业状态，从记录的工作包继续。只阅读相关设计章节和源码，不重复全量调研。若摘要与代码不一致，以可核查事实为准并修正记录。
